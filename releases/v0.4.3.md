# v0.4.3 — Narrative Release Notes Pattern Adoption

**Released:** 2026-04-11
**Type:** CI / infra (backward-compatible, no runtime changes)
**Audience:** Anyone tracking `@luutuankiet/looker-mcp-shim` release history — especially agents picking up context six months from now

---

## TL;DR

Releases up through v0.4.2 shipped with GitHub's `--generate-notes` — which, for a repo that lands most work directly on `main`, produced nearly-empty release bodies that read like "Full Changelog: v0.4.1...v0.4.2". That's useless both to humans and to agents trying to reconstruct the "why" of a given version.

v0.4.3 adopts the per-file narrative release notes pattern already proven on `mcp-proxy-shim` (see [`mcp-proxy-shim/releases/v1.5.0.md`](https://github.com/luutuankiet/mcp-proxy-shim/blob/main/releases/v1.5.0.md)): each tag ships with a hand-written `releases/vX.Y.Z.md` file containing TL;DR → Why → Highlights → Mermaid diagram → Before/After → Upgrade notes. The `publish.yml` workflow now reads that file via `gh release create --notes-file` and **fails loudly if the file is missing** — no silent `--generate-notes` fallback, because empty stubs defeat the point.

There are zero runtime changes in this release. All 57 tools, the safety gates, the upstream bridge, the SDK catalog — everything behaves identically to v0.4.2. This is purely a change in how releases get documented from here forward.

---

## Why This Release Exists

Run `gh release view v0.4.2 -R luutuankiet/looker-mcp-shim` against the current release body and you'll see roughly:

```
v0.4.2
## What's Changed
**Full Changelog**: https://github.com/luutuankiet/looker-mcp-shim/compare/v0.4.1...v0.4.2
```

That's the entire release body. It's what `gh release create --generate-notes` produces when the repo hasn't been using PR-driven workflows. The categorized-commits improvement from conventional commit prefixes (`feat:`, `fix:`, etc.) is one step better, but it's still a mechanical bullet list with no narrative arc, no diagrams, no before/after example, and no "why this exists" — the things that actually help a future reader (or agent) understand what changed.

Meanwhile, the sister project `mcp-proxy-shim` had just adopted a per-file narrative pattern — one `releases/vX.Y.Z.md` per tag, hand-written, pitch-quality, with Mermaid diagrams that GitHub renders natively in release bodies. Its v1.5.0 release notes read like a product announcement, not a changelog. That's the bar.

Applying the same pattern here means:

1. Future releases of `looker-mcp-shim` get release bodies worth reading six months later.
2. The two projects share identical publish infrastructure — change one, port the diff to the other.
3. Agents working on this package can grep past `releases/*.md` for voice, structure, and prior decisions without re-training.

## Highlights

| Change | What it does | Why it matters |
|---|---|---|
| **`releases/README.md` index** | Documents the authoring pattern: TL;DR → Why → Highlights → Mermaid → Before/After → Upgrade notes | New contributors find the convention without spelunking through git history |
| **Per-file release notes** | One `releases/vX.Y.Z.md` per tag, append-only, no monolithic CHANGELOG.md | Conflict-free across parallel branches; cold-reader friendly; git-archaeology friendly |
| **`publish.yml` fail-loud gate** | Release job verifies `releases/${{ github.ref_name }}.md` exists, exits 1 if missing | No silent empty-release stubs; forces authors to write the file before tagging |
| **`gh release create --notes-file`** | Workflow reads the narrative file verbatim for the release body | Mermaid diagrams render natively; formatting stays exactly as written |
| **Zero runtime impact** | No changes to `src/`, `skills/`, tool surface, or published artifact shape | Upgrade from v0.4.2 is literally `npm update` — no behavior drift |

## Before / After

### Before (v0.4.2 release flow)

```yaml
# .github/workflows/publish.yml — release job
release:
  runs-on: ubuntu-latest
  needs: test
  steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0
    - name: Create GitHub Release with auto-generated notes
      env:
        GH_TOKEN: ${{ github.token }}
      run: |
        gh release create "${{ github.ref_name }}" \
          --title "${{ github.ref_name }}" \
          --generate-notes
```

Resulting release body on GitHub:

```
## What's Changed
**Full Changelog**: https://github.com/luutuankiet/looker-mcp-shim/compare/v0.4.1...v0.4.2
```

That's it. No context on what changed, why, or what it means for consumers.

### After (v0.4.3 release flow)

```yaml
# .github/workflows/publish.yml — release job
release:
  runs-on: ubuntu-latest
  needs: test
  steps:
    - uses: actions/checkout@v4
    - name: Verify release notes file exists
      run: |
        NOTES_FILE="releases/${{ github.ref_name }}.md"
        if [ ! -f "$NOTES_FILE" ]; then
          echo "::error::Missing $NOTES_FILE. Every tag needs a hand-written narrative entry."
          echo "::error::See releases/README.md for the authoring pattern."
          exit 1
        fi
    - name: Create GitHub Release from narrative notes file
      env:
        GH_TOKEN: ${{ github.token }}
      run: |
        gh release create "${{ github.ref_name }}" \
          --title "${{ github.ref_name }}" \
          --notes-file "releases/${{ github.ref_name }}.md"
```

The release body is whatever the author wrote in `releases/v0.4.3.md` — this file itself, rendered natively with Mermaid diagrams, tables, and prose.

## Upgrade Notes

- **No breaking changes.** Consumers on v0.4.2 upgrade with `npm update @luutuankiet/looker-mcp-shim` — same API, same tool surface, same safety gates.
- **Contributors: new pre-tag requirement.** Every future tag (`v0.4.4`, `v0.5.0`, …) must ship with a `releases/vX.Y.Z.md` file committed BEFORE the tag is pushed. The workflow fails loudly if the file is missing.
- **Earlier releases predate this pattern.** v0.4.2 and earlier release bodies remain as auto-generated on GitHub; no retroactive backfill. Going forward, this file is the template.
- **Authoring guide.** See `releases/README.md` for the structural template and voice guidance.

## The Hard Truth

This release ships nothing that changes what the package *does*. No new tools, no bug fixes, no performance wins. It exists because release-notes quality compounds over time, and every tag we ship with a hollow body is a unit of context debt that future readers will pay for.

The change took ~30 minutes to land. The narrative files it enables will still be useful years from now. That trade is obvious in retrospect — we should have started with this pattern from v0.1.0.

Thanks to `mcp-proxy-shim` v1.5.0 for proving the pattern first, and for setting the bar high enough that this package couldn't credibly skip it.
